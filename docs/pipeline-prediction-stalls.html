Pipeline prediction on the submission thread

What prediction does

A render pipeline that is not built yet is compiled on the submission thread when a draw needs it. On the first such miss of a submission, pso_get first scans the rest of that submission (pso_predict_rest: state only, no drawing), works out the pipeline keys of the later draws, and starts compiling the missing ones on background threads. When the submission thread reaches one of those draws it takes the pipeline, or waits for what is left of its compile (pso_pend_take). A scan also guesses the other ways the pass may attach depth / stencil (which planes a pass attaches is decided only when it begins, ds_scan); wrong guesses only cost background work. TOTK_PSO_PREDICT=0 turns prediction off.

What PR #29 changed, and the follow-ups

  • No program is resolved for a guess. The scan used prog_get, which translates and compiles a program the first time it is seen. Every new program of a submission was therefore translated and compiled on the submission thread before the current draw, while nothing had been started in the background yet. Now a guess uses only a program that is already resolved, and only the variant for the binding state at that draw (prog_prediction_stages); the program's active variant is not changed. New programs are left to their draws.
  • The scan keeps the future pass's render targets (R.rt), so a fragment variant's signature describes the pass it will draw in.
  • Bounded. At most 8,192 commands, 64 keys per queue and 2 ms per scan; keys with the pass's own attachments start as soon as they are found, the other attach modes after the scan. TOTK_PSO_PREDICT_SCAN, TOTK_PSO_PREDICT_KEYS (up to 160) and TOTK_PSO_PREDICT_US change the three limits; the log prints them once. The time is checked between commands, so it is not a hard bound on descriptors or driver calls.
  • Stale guesses are freed. The pending table has 768 slots. A guess no draw takes (a wrong attach mode, a draw that did not happen) used to keep its slot forever; after a few scans the table was full and nothing was predicted any more. Now a completed guess no draw took is freed two submissions later. A slot whose compile has not finished is never reused: its worker still writes into it.
  • Follow-ups (MacNativeGames): a program with a stage not translated yet (missing, iOS) is not predicted (its draws are skipped, and its fragment stage may be absent); a fragment function that exports depth gets no guesses without the depth buffer (pred_guess_wanted: ds_scan attaches the depth buffer for it, so those guesses were never used, and pso_desc compiled their depth-less library on the submission thread); a statistics line every 100 scans (并行预编 至提交 …: scans and the budget that ended them, pipelines started, pipelines taken by draws and how long draws waited for them, guesses refused because the table was full, stale guesses freed).

Scanning on after a budget

A submission was scanned once, at its first miss. When that scan stopped at a budget (in a world entry almost always the 8,192 commands), the rest of the submission was never predicted and its new pipelines were compiled on the submission thread one after another (265 in one frame, 2.6 s, on entering a new area). Now the next miss of the submission scans again from there, up to 32 times (TOTK_PSO_RESCANS, 0 = one scan as before); keys already compiling are skipped, so each scan moves on. The statistics line also counts the pipelines compiled on the submission thread.

Programs and binding variants not drawn yet

After PR #29 a scan skipped every draw whose program the game had not drawn yet, or whose binding state needs a variant the program had not drawn with (prog_prediction_stages takes only pr->sh / pr->alt). In a world entry those are most of the new pipelines, and their shaders are usually loaded already: the warm-up compiles the prepared shaders' libraries before the player enters the world, and another program may have loaded the same shader. Their pipelines were nevertheless compiled one after another at their draws.

Now such a draw is resolved the way the draw will resolve it, without translating or compiling (prog_prediction_unseen): the shader key from the control section and code (shader_key_of, the same function prog_get uses), the variant from the translation cache's index with the draw's bound state (totk_rt_variant_cached, the lookup totk_rt_variant does before it would translate), and the shader only from g_shcache, which holds the loaded ones. A variant the index does not name, or one no shader is loaded for, is skipped as before. No program is created and no program's variants change; the draw later resolves the same shader objects, so its pipeline key is the predicted one and it takes the pipeline from the pending table. The pipeline is built from the same descriptor as before (pso_desc of the same key), so the picture cannot change. Shader keys are kept per program serial, and the answer for a program and binding signature is kept for the rest of the scan. TOTK_PSO_PREDICT_UNSEEN=0 turns this off. The statistics line gets a second line: draws scanned whose program or variant was not resolved, how many of them were predicted, and the time spent looking them up and building the predicted pipelines' descriptors.

Libraries of unseen variants

A variant the scan finds in the translation cache's index whose Metal library nothing has compiled yet (the warm-up has not reached it, it is off, or Metal's cache lost the library) was skipped, and its draw compiled the library on the submission thread, then the next draw the next library, one after another. Now the scan starts that library's compile on a background thread (plib_kick; as many side by side as the warm-up uses before the world: the cores less two, at most 8), and shader_get at the draw waits for that compile instead of starting its own (plib_take). Draws still wait for their shaders and pipelines; only the compiles run side by side and earlier. Once a library is compiled, a later scan of the submission (PR #166) predicts the pipelines that use it. Only the variant the draw will use is compiled, not every variant of the shader. The Mac only: iOS loads prebuilt libraries. TOTK_PSO_PREDICT_LIBS=0 turns it off; the statistics line counts the libraries started, taken by draws and the time draws waited for them.

Neither did a player's own setup with Metal's caches cleared (their profile and its collected list, the pipeline archive, native 4K): the warm-up builds the listed pipelines and their libraries (9,429 pipelines in 65 s in the background), so 4 libraries were left for this route's world (0.3-0.5 s of stall in both builds, GPU p50 6.6-6.8 ms). The change matters where no list reaches, with a cold Metal cache, as in the table above.

Still done on the submission thread

  • pso_desc for each guess, but no longer the patched functions it needs: a vertex function patched for varyings the fragment reads but the vertex shader does not write (vs_fn_for) or a depth-less fragment function (fs_fn_without_depth) not compiled yet is compiled in the background (variant_defer, the async variants' queue), and the guess is left to a later scan or to its draw. Predicting unseen programs met many such pairs: in one run building the guesses' descriptors took 571 ms on the submission thread, with a 2.0 s frame.
  • ds_scan at the start of each pass calls prog_ps_writes_depth → prog_get, which can translate and compile a program of that pass. This is the path the pass needs anyway.
  • A new program, or a new binding variant, whose variant is not in the translation cache: translation at its draw (with async shaders off), then its library and pipeline. A library whose variant is cached but which a scan did not reach in time is still compiled at the draw.

Checks

scripts/verify_gfx.py (make probe-gfx, no GPU drawing): prediction leaves the active scissor, conditional counters and bindings untouched; an unresolved future program is skipped without translation or compilation; a cached alternate variant is used without being selected; a missing variant is skipped; a program with an untranslated stage is skipped; a depth-exporting fragment gets no depth-less guess; old completed slots are freed, recent ones and unfinished ones are kept; an unseen program and an unseen binding variant of a drawn program are predicted from loaded shaders through the variant index, with the variant of the draw's bound state, without loading a library, creating the program or adding to its variants, and a variant the index names but no shader is loaded for is not predicted; its library is requested for the variant of the draw (recorded, not compiled, in the probe), a scan uses it once compiled, and a draw takes it, waiting while it compiles. TOTK_PROBE_NEGATIVE=24 (take the active variant whatever the state), 25 (free every slot), 26 (ignore untranslated stages), 27 (guess depth-less pipelines for depth export), 28 (look the unseen variant up without the draw's bound state), 29 (record it in the program), 30 (create the program) and 31 (the draw does not wait for a library compiling for prediction) each make the probe fail at its own check.

In-game comparison (1.2.1, Apple M4, 2026-10-19)

Copies of a field save and of the player's shader cache; warm-up off (DM_PSO_MANIFEST=off), so the route meets many pipelines for the first time; after the save loads, the player is moved to Kakariko, Hateno, Rito and Goron, 40 s each. Long frames are the entries of the long-frame log between the first and the last move.

One session each, and another agent built and tested on the same Mac in between (a build overlapped the start of the first row's session): the rows differ by no more than a session varies. No speed-up is claimed either way.

  • Before the change the pending table was full by the end of the loading screen (about 500 guesses in the first 14 scans, 384 slots); in the world a scan could start only one or two pipelines. Prediction was effectively off.
  • With the change: no guess refused, 4,240 stale guesses freed, 5,113 pipelines started in the background and 859 taken by draws; 120 of 200 scans stopped at the 8,192-command budget (0.51 ms per scan on average).
  • Most of the stall on this route is programs seen for the first time: translation, library and then their pipeline. Prediction leaves them alone by design, and their cost is the same whether it is paid during the scan (before) or at the draw (now). What removes them from play is the shared shader list (docs/shader-list.md), whose rows the warm-up builds before the world shows.

The contributor's observation

On an Apple M3 (24 GB, macOS 27.2, game 1.0.0) one session logged 32 long frames above one second, all with library or pipeline creation; the worst was 10,384.9 ms of submission and presentation with 17.5 ms of GPU time. With a broader local build (it also prefetched shaders, which is not part of this change) the player found severe stalls much reduced. That was not a same-route comparison of this change alone.
