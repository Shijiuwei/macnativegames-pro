Breath of the Wild 1.9.0 port: test record

Breath of the Wild (BOTW) 1.9.0 with both DLC packs builds and runs on the BOTW 1.6.0 port of this repository. Both versions use the runtime and the NVN-to-Metal layer of Tears of the Kingdom (TOTK) in games/totk. The BOTW pins and shader list are in games/botw/assets. Code for both BOTW versions is behind GAME_BOTW, code for one version behind GAME_BOTW160 or GAME_BOTW190.

Mac only: Apple M1 Pro, 16 GB, macOS 27.0, built-in 120 Hz Liquid Retina XDR display (3456x2234), 2026-10-20 and 2026-10-21. Each section names its build and settings. The last build tested in game is 3801224 (origin/main 610d735 merged). The build hashes name commits of the development branch, which this PR adds as one commit. "Not tested and known issues" lists what this record does not cover.

Build

Inputs: the base game NSP (01007EF00011E000) as the game file, the 1.9.0 update NSP (01007EF00011E800) with --update, and --firmware (an unpacked firmware NCA folder) or --shared-fonts for the six shared fonts, which an NSP does not hold. Each DLC NSP (01007EF00011F001, 01007EF00011F002) is optional and goes on its own --dlc. A pack that is left out is removed from the work folder, so the app holds the given packs only.

python3.14 build_app.py ~/Games/botw-base.nsp -k ~/keys/prod.keys --update ~/Games/botw-1.9.0.nsp \
    --dlc ~/Games/botw-dlc-1.nsp --dlc ~/Games/botw-dlc-2.nsp --firmware ~/Games/firmware

build_app.py picks the game by the title IDs in the file, never by its name. A card image builds 1.6.0. A base NSP needs --update: with the 1.9.0 update it builds 1.9.0, with the 1.6.0 update 1.6.0 (by the update's verified ExeFS hashes). A package on the wrong option stops the build and names the option it belongs on. --dlc with a 1.6.0 card image or with TOTK also stops the build. A build with a separate update (1.9.0 or 1.6.0) takes its DLC packs from --dlc only. Both BOTW versions use the work folder BotW_build, the app Breath of the Wild.app and the data folder ~/Library/Application Support/MacNativeGames/BotW.

  • Code: games/botw/scripts/extract_exefs.py (upstream #117) takes the ExeFS from the update NSP. The rewriter is unchanged: its generic jump-table detector already rewrites the three 1.9.0 modules to the pinned bytes.
  • Data: games/botw/scripts/extract_romfs.py --update (upstream #117) merges the base and 1.9.0 RomFS (hactool BKTR), verifies every IVFC level and gives the pinned image in 206 s. games/botw/scripts/extract_dlc.py verifies all six IVFC levels of each pack's Data NCA (verify_ivfc, split out of extract_romfs.py). It writes extracted/botw190/aoc/<index>, the layout of the 1.6.0 card that prepare_romfs_backend.py --aoc and runtime/aoc_romfs.c already read.
  • Runtime: make runtime-botw190 in games/totk compiles the 1.6.0 runtime sources with -DGAME_BOTW=1 -DGAME_BOTW190=1, and its own graphics objects in build/gfx-botw190.

Runtime: what differs from 1.6.0

1.9.0 has the game code of 1.6.0 with the SDK 20.5 of a later build. The runtime answers the differences:

  • game_version.h has a GAME_BOTW190 block: folder botw190, and the nnMain and ShowKeyboard addresses of 1.9.0.
  • nn::init::Start takes five arguments (SDK 20.5, as TOTK), not the four of SDK 7. NVN reports version 55.15, the TOTK value, not 53.311.
  • Three calls that 1.6.0 never makes now have answers. nn::account::PopOpenUsers gives the one local user. nn::pl::IsRunningOnOunce answers no, so the game takes the paths of the original Switch. Audio renderer commands 12 and 13 keep the voice-drop parameter and give it back. The mixer never drops voices.
  • Real time at any frame rate (game_patches_botw.c, the #else branch of GAME_BOTW160). Four parts follow the measured frame step: the VFR ratio (ksys::VFR::calc, main+0x151d484/48c), the fade (main+0x125f118/11c/128), the UI animation step (main+0x1280ecc/ee4) and the controller's held counts (main+0xeb0f78/80). Physics keeps six substeps a frame at any frame rate (main+0x128106c fmov s9, #1.0), as on 1.6.0. 1.9.0 counts held frames in floats, so the ratio is the step and no tick is needed. The fast-repeat countdown of the pause menu already reads the VFR's delta frames. Each patch checks the original words first. verify_realtime_patch.py and verify_pad_repeat_patch.py with --version botw190 run the words of the C file in Unicorn, with negative controls, for the UI step and the physics substeps too. In one game run, uncapped play (menus about 118 FPS, Great Plateau 69-76 FPS) and key 2 at 30+30 (29-30 FPS) gave the same speed, within one 30 fps frame, for the inventory tab animations (R, L), the typed item text and the jump poses (X, 100 ms steps). A frame-driven animation would be 4 times slower. At 30 fps the inventory opens about 80-120 ms later (about 3 frames), then runs at the same rate.
  • Docked play renders at 1920x1080, as upstream's 1.6.0 port does: the display-mode routine main+0x1266074, movk at main+0x12660c8. TOTK_RENDER_RES=900 keeps 1600x900.
  • While a movie plays (movie player instance main+0x1e565a8), the pacing holds 30 fps. Every movie frame is shown (MOVIE_PACE_DEFAULT 0 for both BOTW versions, upstream's value). The first tower's movie plays at 31.7 fps, and the game goes on after it.
  • MetalFX keys 2 and 3: 1.9.0 upscales the 1600x900 picture into the 1920x1080 canvas with its own fragment shader (bd7ffdd4, nine texel reads). BOTW_MFXUP_KEY in nvn_obj.h is the upscale key of the version that is built. In docked play at 1920x1080 that draw is no upscale, so key 3 upscales the window output only.
  • Key 5 (MetalFX temporal anti-aliasing): the scaler runs before 1.9.0's compose draw f7ee6fe1 (tone mapping). Its t0 is the R11G11B10F scene and t1 the 320x180 bloom. The scene is 1920x1080 in docked play, 1600x900 before that patch. TAA_COMPOSE in nvn_obj.h holds the compose key of each game. The jitter and the camera block need no change. Upstream's #157 picks the jittered draws by what they do, not by a shader key, so it acts on BOTW too. 1.6.0's compose key is not known, so key 5 has no effect there.

Two changes act on both BOTW versions:

  • Write-back staging: the game invalidates 1x1 and 3x3 GPU-written textures every frame. The write-back waited for all GPU work (mtl_finish_gpu) and made one blit round trip per texture on the game thread. On an earlier build of this port, Kakariko ran at 49 FPS. Now the submission that renders such a texture (256 KiB or less) copies it into a shared stage buffer at its end. The invalidate waits only for the fences of the listed renderings and swizzles a staged texture from its stage. Larger textures keep the read-back blit. With staging, Kakariko holds 59.5 FPS at the 60 FPS cap. A timer in a test build measured the stage copies at 107 us per game frame (103-113 us, 14 copies and 4.7 new buffers a frame). That is 1.3 % of a 120 FPS frame.
  • Grass masks (after f1043e5): the game flushes its 512x512 grass density mask right after rendering it and reads it on the CPU to choose the grass cells 50-130 m away. The flush write-back waited about 3.7 ms a frame for that rendering. A target the flush has had to wait for 120 times (1 MiB at most) now lands in memory when its submission completes, and the flush no longer waits: the CPU reads the last completed mask, as on hardware, where the game does not wait for it either. This also learns the 64x64 light-probe cube maps. Great Plateau at the 120 FPS ceiling: 114-120 FPS and p99 11.7-15.6 ms before, 119.6-120 FPS and p99 10.6-11.0 ms after. TOTK_BOTW_LATE_WB=0 restores the waiting write-back. probe-gpu-writeback covers the landing, neighbour and own CPU writes on the shared edge pages, and a short pool.
  • 120 Hz displays: the uncapped mode stays off on a display of 120 Hz or more (UNCAPPED_HZ). The BOTW rule that ignores the game's present interval 2 acted only in that mode, so BOTW ran at 60 FPS on a 120 Hz display. The display-following path now ignores interval 2 in the same cases: real time, DM_PRESENT_HZ unset, TOTK_UNCAPPED, TOTK_FPS60 and TOTK_UNCAPPED_INTERVAL not 0, and no deterministic clock. Interpolation at half rate or 30+30 keeps its own pacing. The result is one game frame per refresh, up to 120 FPS. The log names the opt-out.
    • Replaced after the merge (user 2026-10-22): the uncapped mode applies on any display, so this rule is gone. Its clock's ceiling went to 240, then back to 120 by default the same day (user; TOTK_UNCAPPED_HZ still allows up to 240). The real-time frame step lost its 1/120 s floor (TOTK and BOTW), which made a game above 120 fps run fast; the Unicorn checks of both versions pass at 144, 165, 240 and 360 fps.
    • The display link that shows the uncapped frames keeps a display rate above 120 Hz too, up to 240 (link_range in nvn_mtl.m; TOTK and BOTW). It turned such a rate into 60, so a 144 / 160 Hz display ticked at a divisor of its refresh: on a 160 Hz display about 53 frames a second reached the screen, 18.75 / 25 ms apart, while the game ran at 105-120 fps. Only an unknown rate (below 30) still falls back to 60.

Write-back staging A/B on 29bc388, with upstream's #140 and #143 in the build: Kakariko, uncapped, docked 1920x1080 render, warm shader cache v6, still view from 115 s for 20 s, then a 15 s walk. The "off" build used the TOTK hooks. Still view: 66.8 fps with staging, 55.5 without (p50 / p95 14.4 / 18.7 ms against 17.5 / 23.3 ms, 212 against 706 frames over 16.7 ms). Walk: 55.7 and 49.2 fps. The GPU time p50 is the same (10.3 and 10.2 ms). Without staging, the game thread waits for all GPU work at each invalidate, and #143 does not change that wait.

Key 4, ultrawide (2026-10-21)

The main camera is a sead::PerspectiveProjection at +0x38 in a singleton (pointer main+0x1e39d10, made at main+0x10ed664, vtable main+0x1d05380, aspect at +0xb0, dirty flag at +8). The game sets the aspect once and rebuilds the matrix every frame. So while key 4 is on, the present writes the wide ratio into the field and marks it dirty. Only a 16:9 value is replaced, and another class stops the game. The values come from in-game diagnostics: a scan of live projections by their vtable, a pointer scan of main's data, and a 25 s write watch that saw no writes in play.

The present stretches the 16:9 canvas over the window. The UI is squeezed back to the middle 16:9 (UW_UI_BEGINS, UW_NOT_UI_DRAW in nvn_obj.h). Every 6-index quad into the canvas is squeezed, except quads that sample a GPU-rendered 16:9 picture at least 320 pixels wide (the menus' blurred game picture). Full-screen triangles keep the full width.

Upstream's key 4 (#120) cycles 16:9, fit to the window and 21:9 on TOTK. On 1.9.0, key 4 switches 16:9 and the wide ratio only (TOTK_ASPECT, default 21:9): runtime_aspect_step answers 0 or 2, and the window size is not followed. On 1.6.0, runtime_aspect_view and runtime_aspect_step are stubs.

Tested on the Mac, 2520x1080 window, TOTK_ASPECT default 21:9:

  • Great Plateau and Kakariko: a wider view with correct proportions, the HUD in the middle.
  • The inventory: the UI and Link are correct, and the blurred background is full width. A faint edge shows where the menu's dim layer ends. The map: 16:9 with black bars.
  • TOTK_ASPECT=21:9 starts wide, and key 4 goes to 16:9 and back. At 6aa1821, TOTK_ASPECT=display stops at the start with the parser's message.
  • Kakariko standing still, one run each: key 4 off 62.9 fps, on 65.0, off 64.1. GPU p50 9.75, 9.69 and 9.67 ms: no measurable cost.

Not tested: 1.6.0 (key 4 stays unavailable there), iPhone and iPad (Mac only by design), cutscenes, shrines, other menus (Adventure Log, System, shops), a real ultrawide display in full screen, and long play. A second camera-like projection stays 16:9. No objects were seen culled at the screen edges in the tested places. Markers that follow objects in the world are not moved out yet.

Audio: volume ramps and depop (2026-10-22)

The mixer applied a new voice volume or channel mix volume as a step at the 5 ms frame edge, and a stopped or paused voice dropped to zero at once. BOTW ducks the music when the pause menu or the map opens, and each step on a loud sample is a click. The Switch DSP ramps the voice volume and each channel's mix volume from the last frame's value and decays a stopped voice's last samples (Ryujinx.Audio CommandGenerator.GenerateVoice: VolumeRamp, MixRamp, DepopPrepare, DepopForMixBuffers, 0.962189 per sample at 48 kHz). audio_mixer.c does the same under GAME_BOTW; TOTK_AUDIO_RAMP=0 gives the old mixer for a comparison.

  • tests/test_audio_ramp.c (CI, no game data) runs audio_ramp.h: a duck from 1 to 0.25, a mix volume that falls to 0 and a stopped voice's decay may not step a sample by more than 0.04. With -DAUDIO_RAMP_STEP it fails (steps 0.6, 0.4 and 0.5).
  • make probe-audio-botw190 (needs game data): a 0.8 voice ducks and stops, no sample steps more than 0.04. Run on the packaged binary of this branch (origin/main daf270e): it passes, and with TOTK_AUDIO_RAMP=0 it fails with "volume step or stop is not smoothed".
  • The same probe has three edge cases of the depop: a voice that is stopped and then released, or reused by a new voice, before the next frame still fades from its last sample, and a voice whose channel was muted for a frame adds nothing when it is paused afterwards (its last added sample is 0). Run on a build of origin/main a988b5e with this branch's runtime: without the fix the release and reuse cases step 0.8 and the mute-then-pause case adds 0.0032; with it the probe passes (and fails with TOTK_AUDIO_RAMP=0). A voice freed while it is still started is cut. When a new voice starts at once in the place of a stopped one, the old tail still fades and the new voice ramps up from 0 over its first frame, so the two do not add to a clipped step (0.8 plus 0.77 would clip to 1.0) and a silent new voice does not cut the tail to 0.
